# DAG creation — how the graph artefact is built

> ## ⚠ Superseded — this describes the ORIGINAL graph, not the current one
>
> This document explains the hand-authored 49-edge DAG produced by
> [`causal/build_ctp_causal_dag.py`](../causal/build_ctp_causal_dag.py). That graph has been
> **replaced** by the evidence-based pipeline in stages 0–15, whose output is
> [`causal/provenance/banded_graph.json`](../causal/provenance/banded_graph.json) and
> [`causal/ctp_reviewed_dag.html`](../causal/ctp_reviewed_dag.html) — currently 34 edges, each
> traceable to statute, a tested prior, a domain expert's claim, or a mediator path.
>
> It is kept because the before-and-after is the point of the project: the original graph was
> LLM-generated, described as "expert-elicited", and its 49 edges rested on nothing that could be
> checked. Read this to understand **what was replaced and why**. For how the graph is built now,
> start at [`README.md`](../README.md).


Where [`causal-algorithm.md`](causal-algorithm.md) covers *why* each edge points the way it does,
this document covers the mechanics: the data structures, the build pipeline, the output schema, the
validation gates, and how to change the graph without breaking anything.

---

## 0. Provenance

The `BANDS`, `NODES`, `EDGES` and `MISSING_*` literals described below were **generated by a large
language model** (Claude) from its training knowledge of NSW CTP scheme mechanics. **No domain
expert has reviewed them.** Earlier wording in this repository called the graph "expert-elicited";
that was inaccurate and has been corrected.

This matters for two things this document describes:

- **`strength` is not a blinded prior.** The docs previously claimed signs and strengths were fixed
  before the correlations were computed. There is no record establishing that, and the same process
  produced both.
- **The build's assertions check structure, not truth.** Acyclicity, band ordering and column-name
  validity all pass on a graph whose arrows point the wrong way. They are necessary, not sufficient.

What *is* checked: [`verify_claims.py`](../causal/verify_claims.py) recomputes every descriptive
statistic quoted in the `note` and `mechanism` prose against `ctp/ctp.csv` and exits non-zero on any
mismatch. It caught one drift on first run (a note reading "91%" where the figure is 91.9%). It
verifies numbers only — never an edge direction.

## 1. The pipeline

```
ctp/ctp.csv ──┐
              ├──► causal/build_ctp_causal_dag.py ──► causal/ctp_causal_dag.json
BANDS/NODES/  │                                              │
EDGES (in the │                                              │
script)   ────┘                                              ▼
                    causal/dashboard_template.html ──► causal/build_dashboard.py
                                                                    │
                                                                    ▼
                                                    causal/ctp_causal_dashboard.html
```

Two commands, run in this order:

```bash
python causal/build_ctp_causal_dag.py && python causal/build_dashboard.py
```

Plus the claim check, which is independent of the two build steps:

```bash
python causal/verify_claims.py
```

The JSON is the **single source of truth**. The dashboard does not re-derive anything — it renders
the JSON. Any downstream consumer reads the same file. Nothing in the pipeline is stochastic; the
same CSV produces byte-identical output every time.

## 2. The graph is declared, not inferred

The graph lives as four module-level Python literals in
[`build_ctp_causal_dag.py`](../causal/build_ctp_causal_dag.py). Editing the graph means editing these
lists — there is no separate config file, no YAML, no database. The rationale is that each edge needs
a prose justification attached to it, and a Python tuple with a docstring-length final element does
that better than any serialisation format.

### 2.1 `BANDS` — the causal-temporal layers

```python
{"id": "clinical",
 "label": "Clinical course & capacity",
 "blurb": "How the injury played out: treatment, permanent impairment, ability to work."}
```

Six bands, declared in chronological order. Ordering here is what the dashboard uses for its
left-to-right columns, and it is the human-readable statement of the hard constraint that **no edge
runs backwards**.

| # | `id` | Label | Nodes |
|---|---|---|---|
| 1 | `claimant` | Claimant, pre-accident | 4 |
| 2 | `injury` | Accident & injury | 3 |
| 3 | `clinical` | Clinical course & capacity | 3 |
| 4 | `dispute` | Dispute & forum | 3 |
| 5 | `heads` | Heads of damage | 2 |
| 6 | `award` | Award | 1 |

### 2.2 `NODES` — 16 variables

```python
dict(id="WPI %", short="WPI %", band="clinical", kind="numeric",
     x=586, y=92,
     note="Whole Person Impairment from the medical assessment. The statutory gate for "
          "non-economic loss (>10%). 46.9% missing — recorded only when it was assessed.")
```

| Field | Purpose |
|---|---|
| `id` | **Must match the CSV column name exactly.** This is the join key against `ctp.csv`; a typo surfaces as a `KeyError` during the correlation pass. |
| `short` | Display label for the dashboard, where the full name does not fit in a node box. |
| `band` | One of the six band ids. Determines vertical placement and the ordering constraint. |
| `kind` | `numeric` / `ordinal` / `categorical`. Consumed downstream to choose a regressor vs a classifier; not used by the build itself. |
| `x`, `y` | Dashboard layout coordinates in SVG user units. Hand-placed — see §5. |
| `note` | Prose. What the variable is, why it sits where it sits, and any measurement caveat (missingness rate, near-constancy, unobserved parents). |

Full inventory, in declaration order:

| Band | Node | `kind` | Note highlight |
|---|---|---|---|
| claimant | `Claimant Age` | numeric | Root. 8.1% missing. |
| claimant | `Claimant Gender` | categorical | Root. Enters via earnings and occupation mix. |
| claimant | `Claimant Weekly Income` | numeric | The economic-loss multiplicand. 41.9% missing, informatively. |
| claimant | `Pre-existing Condition Salience` | ordinal | Child of `Claimant Age` — degeneration accumulates. |
| injury | `Injury Burden Intensity` | ordinal | 0–4. Accident forces are unobserved, treated as exogenous noise. |
| injury | `Psychological Injury Emphasis` | ordinal | 0–2. |
| injury | `Liability Clarity` | ordinal | 0–2. Near-constant (91.9% at top level) but genuinely exogenous. |
| clinical | `WPI %` | numeric | The statutory gate. 46.9% missing. |
| clinical | `Treatment Burden` | ordinal | 0–3. |
| clinical | `Work Impact Severity` | ordinal | 0–3. Driver of economic loss. |
| dispute | `Causation Complexity` | ordinal | 0–2. |
| dispute | `Nature` | categorical | Settlement Approval vs Damages. An *effect* of contest, not a cause of injury. |
| dispute | `Legal Procedural Complexity` | ordinal | 0–3. A leaf — records the dispute, does not set quantum. |
| heads | `Non-Economic Loss` | numeric | Gated on WPI > 10%. 15.4% missing. |
| heads | `Future Economic Loss` | numeric | 23.5% missing. |
| award | `Lump Sum` | numeric | **Target.** A collider, and column 0 of the CSV. |

### 2.3 `EDGES` — 49 five-tuples

```python
("WPI %", "Non-Economic Loss", "+", "high",
 "STATUTORY GATE. No non-economic loss below the >10% WPI threshold; above it, quantum "
 "scales with the assessed impairment."),
```

`(source, target, sign, strength, mechanism)`:

- **`sign`** — `+` / `-` / `~`. Direction of the *direct* effect with other parents held fixed.
- **`strength`** — `high` / `medium` / `low`. Stated confidence in the mechanism. Not an effect
  size, and not a blinded prior — see the provenance note below.
- **`mechanism`** — the actual justification for the edge. This is what a reviewer reads and
  argues with.

Grouped in the source by band transition, which makes the constraint easy to eyeball while editing:
claimant internals → injury layer → clinical layer → dispute layer → heads of damage → award.

### 2.4 `MISSING_NODES` / `MISSING_EDGES` — the m-graph

Five response indicators and twelve edges, declared separately because **they are not columns of
`ctp.csv`** — a downstream consumer materialises them from the NaN pattern. Keeping them out of
`NODES`/`EDGES` means the main graph stays a clean 16-node picture of the substantive process, and
the augmented 21-node graph is assembled by whoever needs it.

```python
dict(id="R_WPI", target="WPI %", rate=0.469,
     note="WPI is written down only when an impairment assessment was in evidence.")

("WPI %", "R_WPI", "-", "SELF-MASKING. Assessment is sought when the >10% threshold is live, ...")
```

Missingness edges carry `(source, target, sign, mechanism)` — no `strength`, and **no ρ annotation**,
because the indicator columns do not exist in the CSV to correlate against. The evidence for these
edges is stated numerically inside the `mechanism` strings instead (e.g. "42.0% missing vs 49.4%").

## 3. What the build computes

`main()` ([`build_ctp_causal_dag.py:329`](../causal/build_ctp_causal_dag.py#L329)) does six things:

1. **Loads `ctp/ctp.csv`** and binarises the two string columns so associations are computable
   (`Claimant Gender == "Male"`, `Nature == "Damages"`). The contrasts are recorded in the output so
   the sign of every ρ on those edges is interpretable.

2. **Topologically sorts** with Kahn's algorithm, ties broken by declaration order so the result is
   stable across runs. Then asserts every edge runs forward:

   ```python
   for src, dst, *_ in EDGES:
       assert rank[src] < rank[dst], f"back-edge {src} -> {dst}"
   ```

   A cycle raises `ValueError` naming the nodes involved; a back-edge trips the assertion. **Neither
   is recoverable — the build stops.**

3. **Compares to CSV column order**, counting edges whose target precedes their source in the file.
   Currently 34 of 49.

4. **Annotates every edge** with a pairwise-complete Spearman ρ and its `n`, plus two boolean flags:
   `sign_conflicts_marginal` (asserted direct effect disagrees with the marginal, |ρ| > 0.03) and
   `csv_order_violation`.

5. **Measures the collider** at `Lump Sum` — ρ(NEL, FEL) marginal vs. after residualising both on
   `log(Lump Sum)`. Currently +0.513 → −0.459 on n = 348.

6. **Writes the JSON** and prints a summary: counts, the full topological order, and the collider
   numbers.

Console output of a clean run:

```
wrote .../causal/ctp_causal_dag.json
nodes=16 edges=49 csv-order violations=34/49
topological order:
   0. Claimant Age
   1. Claimant Gender
   ...
  15. Lump Sum
collider check: rho(NEL,FEL)=0.513 -> -0.459 given Lump Sum
```

## 4. Output schema — `ctp_causal_dag.json`

| Key | Type | Contents |
|---|---|---|
| `name`, `version`, `target`, `n_rows` | scalars | `"nsw-ctp-severity"`, `"1.0"`, `"Lump Sum"`, `540` |
| `description` | string | What the graph is for and how it was oriented |
| `bands` | list | The six bands verbatim from `BANDS` |
| `nodes` | list | The 16 nodes verbatim from `NODES`, layout coordinates included |
| `edges` | list | 49 objects: `source`, `target`, `sign`, `strength`, `mechanism`, `rho`, `n`, `sign_conflicts_marginal`, `csv_order_violation` |
| `parents` | object | Adjacency as `{node: [parent, …]}` — the conditioning set for each variable |
| `topological_order` | list | The 16 node ids in valid generation order |
| `csv_column_order` | list | The CSV header, for comparison |
| `csv_order_violations` | list | The 34 `[source, target]` pairs the file order reverses |
| `missingness.nodes` | list | The 5 `R_V` indicators with `target`, `rate`, `note` |
| `missingness.edges` | list | The 12 m-graph edges |
| `colliders` | list | `pair`, `collider`, `n`, `rho_marginal`, `rho_given_collider` |
| `categorical_contrasts` | object | Which level is coded 1, per string column |
| `stats` | object | `n_nodes`, `n_edges`, `n_violations`, `n_sign_conflicts`, `missing_rates` |

`parents` and `topological_order` are the two keys a generator actually needs; everything else is
provenance and diagnostics.

## 5. The dashboard

[`build_dashboard.py`](../causal/build_dashboard.py) is deliberately trivial — 30 lines. It reads
`dashboard_template.html`, substitutes the placeholder `__DAG_JSON__` with the minified JSON, and
writes `ctp_causal_dashboard.html`.

The payload lands inside `<script type="application/json" id="dag-data">`, where the only sequence
that can terminate the block early is `</script>`. The script escapes `</` to `<\/` to prevent that.
All markup, CSS and JavaScript live in the template; there are no external dependencies, so the
output is a single file you can open with `file://` or email to someone.

Four views, all driven off the same payload:

| Tab | Shows |
|---|---|
| **Causal map** | The 16-node graph laid out in six bands, edges coloured by sign and weighted by strength. Click a node for its note, parents and children. |
| **Parent → child adjacency** | The 16×16 matrix, toggleable between topological and CSV order. In topological order it is upper-triangular; in CSV order the mass sits below the diagonal — the 34 violations made visible. |
| **Why the order matters here** | The collider card and the seven sign-conflicting edges. |
| **Missingness** | The m-graph and the conditional blank rates that motivate each indicator edge. |

**Node coordinates are hand-placed.** `x` runs 118 → 1274 across the six bands (roughly 234 units per
band); `y` is chosen per node to keep edges from crossing. There is no auto-layout — a layout engine
produced worse pictures than placing sixteen nodes by hand, and the coordinates are stable, which
means diffs to the graph produce readable diffs to the picture.

## 6. Changing the graph

### Adding a node

1. Add a `dict(...)` to `NODES`. `id` **must** be the exact CSV column name. Pick a band, pick a
   `kind`, write the `note`.
2. Choose `x` from the node's band (match its neighbours) and a `y` that does not collide.
3. Add at least one edge — an isolated node is almost always an authoring error.
4. Re-run both build scripts and look at the map. If the new node's edges cross badly, adjust `y`.

### Adding or changing an edge

1. Append the five-tuple to `EDGES`, in the band-transition group it belongs to.
2. Write a real `mechanism`. "Seems related" is not a mechanism; if you cannot write one sentence
   naming the pathway, the edge should not exist.
3. Set `strength` from your prior, **before** you look at the resulting ρ, and record that you did.
   Fitting the annotation to the observed correlation defeats the purpose of the audit — and note
   that the existing graph carries no such record (see provenance, §0).
4. Re-run. If the assertion trips, you have introduced a back-edge — either the direction is wrong or
   the node is in the wrong band.
5. Check whether the edge came out `sign_conflicts_marginal`. That is not automatically a problem
   (see [`causal-algorithm.md` §3.2](causal-algorithm.md#32-sign-conflicts--the-interesting-failures)),
   but it obliges you to say *which* confounder explains the disagreement. If you cannot name one,
   reconsider the sign.

### Adding a missingness indicator

Add to `MISSING_NODES` with the measured `rate`, then add its parent edges to `MISSING_EDGES`. Put
the supporting conditional rates in the `mechanism` string — they are the only evidence these edges
get, since the indicators are not columns.

### Regression check

There is no test suite; the assertions in the build *are* the tests. After any change, confirm:

- the build exits 0 (acyclicity and band ordering hold);
- `stats.n_nodes` / `stats.n_edges` match what you expect;
- the collider numbers have not moved (they should not, unless you changed the CSV);
- the map still reads left-to-right without edge spaghetti.
